# 0001 許可リストの設計

| 項目 | 内容 |
|---|---|
| 状態 | 採用（2026年10月18日） |
| 対象 | 許可リスト（`src/core/allowlist.ts`、設定画面、ポリシーの`enforcedAllowlist`と`allowUserAllowlist`） |
| 英語版 | [0001-allowlist.md](0001-allowlist.md) |

この文書は、許可リストをどういう経緯でどう設計したかを記録します。
許可リストの制限を緩める、または機能を外すPRを出す人は、この文書の判断に対する論理的な反論を示してください（「変更するときの条件」）。

## 経緯

本文のリンクを開くたびにダイアログを出すと、リンクを多く開く人ほど、中身を読まずに「開く」を押す癖がつきます。
同じ警告を繰り返し見ると反応が鈍ることは、警告への慣れの研究でも示されています。
そこで、ふだん使うサイトだけダイアログを省けるよう、許可リストを入れました。

一方で、許可リストはこの拡張機能でいちばん危険な設定です。
検討の中で、次の3つの抜け道を確認しました。

1. 信頼したドメインの中に、だれでもページを作れる場所がある。`google.com`を許可すると、`sites.google.com`に置いた偽のログインページも素通りになる。2026年10月に、Googleの正規の通知を再送してSites上の偽ページへ誘導する手口が報告されている。
2. 信頼したドメインのリダイレクトを使うと、許可したドメインのURLから攻撃者のサイトへ飛ばせる。
3. 正規のサイトが乗っ取られると、許可したドメインそのものが攻撃に使われる。

許可リストを残すかどうかも検討しました。
登録しなければ何も起きない機能なので、使わない人の負担はありません。
効果があるのは、同じ取引先、社内システム、SaaSのリンクを繰り返し開く人と、管理者が社内のドメインを配る組織です。
送り主が毎回ばらばらな人には、ほとんど効きません。
これらを比べ、制限を付けたうえで残すと判断しました。

## 決めたこと

| # | 決めたこと | 防ぐもの |
|---|---|---|
| D-1 | 登録は設定画面からだけにし、ダイアログからは登録できない | 怪しいリンクを前にした勢いでの許可 |
| D-2 | 許可リストはインポートできない。組織ではポリシーで配る | 他人から受け取ったファイルで、気づかないうちに許可が入ること |
| D-3 | 登録はホスト名だけ。URL、ワイルドカード、正規表現では登録できない | 広すぎる指定 |
| D-4 | ホスト名は完全一致。サブドメインは利用者が選んだときだけ含める | 意図しないサブドメインの許可 |
| D-5 | ブロックリストが常に優先する | 許可とブロックの両方に当たる行き先を開くこと |
| D-6 | 注意点が1つでもあるとき（表示との食い違い、Punycode、IPアドレス、`@`、HTTP、共有ホスト、短縮URL）はダイアログを出す | 見た目をごまかしたリンク |
| D-7 | HTTPS（標準のポート）でないときはダイアログを出す | 暗号化されていない接続や、標準でないポートでの待ち受け |
| D-8 | URLのクエリ、パス、`#`以降に別のURLがあるときはダイアログを出す | 抜け道2（リダイレクト） |
| D-9 | 判定はリダイレクトの包み（Google、Safe Links）を外した後の行き先で行う | 包みを使った見せかけ |
| D-10 | 利用者は、だれでもページを作れるサイト（`SHARED_HOSTING`）と短縮URLを登録できない。サブドメインを含めるとそれらを覆う場合も登録できない | 抜け道1（共有ホスト） |
| D-11 | 組織のポリシーでは、共有ホスト上の自社のテナント（例：`contoso.sharepoint.com`）も登録できる | 組織での正当な利用を妨げること |
| D-12 | 組織は、利用者自身の許可リストをポリシーで止められる | 組織の方針と個人の設定の食い違い |
| D-13 | 上限は1,000件 | 実質的に何でも許可する状態 |

## 防げないこと

- 許可したサイトそのものが乗っ取られた場合（抜け道3）。許可リストの仕組みでは防げません。
- `SHARED_HOSTING`に載っていない共有ホスト。一覧は手で保守しており、漏れがありえます。

## 検討したほかの案

| 案 | 採らなかった理由 |
|---|---|
| 許可リストを持たない | リンクを多く開く人の慣れの問題が残る |
| ダイアログから許可できるようにする | D-1のとおり、攻撃者が急がせる場面で許可されやすい |
| URL単位で許可する | 同じURLが繰り返し届くことは少なく、効果がほとんどない |
| 組織のポリシーだけに残す | 個人で使う人が恩恵を受けられない。必要なら組織はD-12で利用者の許可リストを止められる |

## 今後の候補

採用は決めていませんが、次の案があります。

- 登録に期限を設け、一定期間で自動的に外す
- 警告の見た目を毎回変え、慣れを防ぐ

## 変更するときの条件

| 区分 | 意味 | 振り分けの基準 | 満たさなかったときの扱い |
|---|---|---|---|
| MUST | 満たさなければマージしない | 満たさないと、上の判断を根拠なく覆すことになる | マージしない |
| SHOULD | 満たすべきだが、満たさなくてもマージできる | 満たさないと、レビューで判断材料が足りなくなる | 満たさない理由をPRに書く |
| NICE TO HAVE | 満たすことが望ましい | 満たせばレビューが速くなる | 対応しなくてよい |

| # | 条件 | 区分 |
|---|---|---|
| C-1 | D-1からD-13のどれかを緩める、外す、または許可リストを廃止するPRには、該当する項目の「防ぐもの」がなぜ問題にならないか、または別の手段でどう防ぐかを論理的に示すこと | MUST |
| C-2 | C-1の反論が前提とする事実（攻撃の手口、ブラウザの仕様など）には、出典を示すこと | MUST |
| C-3 | 変更後の挙動を確かめる単体テストかe2eテストを付けること | MUST |
| C-4 | この文書の該当箇所を、変更後の判断に合わせて更新すること（日本語版と英語版の両方） | MUST |
| C-5 | 制限を強める変更（`SHARED_HOSTING`への追加など）は、C-1の反論なしで出してよい。理由は1行で書くこと | SHOULD |
| C-6 | 利用者の体験への影響（ダイアログの回数がどう変わるか）をPRに書くこと | NICE TO HAVE |

> C-1の補足：「使いにくいから」だけでは反論になりません。使いにくさを解消した結果、どの抜け道が開くか、それをどう扱うかまで書いてください。
